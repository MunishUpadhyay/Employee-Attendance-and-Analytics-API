# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_work_hours` | Used standard Python float `round()`, which applies round-half-to-even (banker's rounding). Rule R4 requires true round-half-up to two decimal places. | Input `punch_in` and `punch_out` with a 7,650-second difference (2.125 hours). Python `round(7650 / 3600, 2)` returns `2.12` instead of `2.13`. | Replaced float arithmetic with Python `Decimal` and `.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 2 | `compute_late_minutes` | Divided seconds by 60 before checking `minutes > 10`. Also anchored the shift start to the calendar date of the punch-in instant, breaking overnight shifts. | A punch-in 10 minutes and 15 seconds after shift start resulted in `int(615 / 60) = 10`, failing `> 10` and incorrectly returning 0. For an overnight shift (22:00–06:00), punching in at 01:00 on the following calendar day anchored shift start to 22:00 that night (-21 hours elapsed), returning 0 instead of 180. | Evaluated raw seconds difference against `600` seconds (`diff_seconds > 600`), took `int(diff_seconds // 60)`, and anchored shift start to the record's attendance date in IST. |
| 3 | `compute_overtime` | Returned raw positive minutes without enforcing R3's 30-minute minimum threshold. Also failed to handle overnight shifts where `shift_end <= shift_start`. | Punching out 15 minutes after shift end returned 15 overtime minutes instead of 0. For an overnight shift (22:00–06:00), punching out at 06:40 IST computed overtime relative to 06:00 on the previous calendar day (+24 hours). | Required `diff_seconds >= 1800` (returning 0 otherwise), added one calendar day to shift end when `shift_end <= shift_start`, and ensured timezone-aware comparisons. |
| 4 | Startup / Lifespan | No database indexes were defined or created at application startup. | Listing and analytics queries on large collections performed full collection scans (`COLLSCAN`), and duplicate records were permitted by MongoDB because no unique indexes existed. | Added a FastAPI `lifespan` handler creating idempotent unique and compound indexes on `employees` (`emp_code`, `(department, emp_code)`, `joined_on`) and `attendance_logs` (`(emp_code, date)`, `(date, emp_code)`, `(emp_code, punch_in)`). |
| 5 | `create_employee` | Returned un-serialized Python `datetime` in `created_at`, and lacked whole-second truncation. | The response body serialized `created_at` as an ISO 8601 string instead of the required integer epoch milliseconds (`EpochMillis` schema). | Truncated microseconds with `.replace(microsecond=0)` and passed documents through `serialize_datetimes()` to convert BSON UTC datetimes to epoch milliseconds. |
| 6 | `punch_in` | Exposed internal MongoDB `_id` by attaching `doc["id"] = str(res.inserted_id)`. | The HTTP response leaked internal database object IDs, violating the contract where attendance records have no ID. | Removed `doc["id"]` and stripped `_id` before returning the response. |
| 7 | `punch_in` | Returned un-serialized `punch_in` datetime, accepted invalid presence statuses, lacked timestamp bound validation, and did not truncate instants to whole seconds (R1). | Punching in with status `ABSENT` or `LEAVE` succeeded instead of returning 422. Fractional seconds (e.g. `09:40:00.900`) were not truncated. The response returned an ISO timestamp string instead of integer epoch milliseconds. | Restricted status to `PRESENT`, `WFH`, and `ON_DUTY`, validated epoch millisecond boundaries, normalized timestamps with `.replace(microsecond=0)`, and serialized instants to epoch milliseconds. |
| 8 | `punch_in` | Did not assign attendance dates correctly for overnight shifts (R1). | For an overnight shift (22:00–06:00), punching in at 01:00 on calendar date D+1 assigned the record date to D+1 instead of D. | Evaluated if `shift_end <= shift_start` and punch-in time is before `shift_end`, assigning the attendance date to the previous calendar day. |
| 9 | `list_employees` | Returned raw database items without serializing `created_at` datetimes to integer epoch milliseconds. | Items contained ISO datetime strings instead of integer epoch milliseconds. | Passed items through `serialize_datetimes()` to convert datetimes to epoch milliseconds. |
| 10 | `list_attendance` | Did not populate default values for missing derived fields in seeded records, and used an untyped string for status. | Seeded records omitting `half_day`, `history`, `late_minutes`, or `overtime_minutes` failed schema validation on output. | Populated default values (`half_day: False`, `history: []`, `late_minutes: 0`, `overtime_minutes: 0`) and typed the `status` query parameter against the `Status` enum. |

### Also noted and decided was NOT a defect:

1. **PyMongo Naive Datetimes:** PyMongo returns naive UTC datetimes by default. Rather than replacing client options, explicitly tagging naive instants with `tzinfo=timezone.utc` and converting to IST at the service boundary was verified to be correct, robust, and consistent across platforms.
2. **Case-Sensitive Department Filtering:** In `GET /employees` and analytics queries, department matching is case-sensitive. The OpenAPI specification specifies exact string matching for department names, so case-insensitive regex matching was intentionally avoided.
3. **No Authentication Headers:** The starter endpoints lacked authentication or authorization middleware. The problem statement explicitly states that authentication is out of scope for this assignment (`regularized_by` is free text).
4. **Shift Times Equality Validator:** `EmployeeIn` already included a model validator ensuring `shift_start != shift_end`. This was examined and verified to function as intended.
5. **Date Range Comparison in List Attendance:** `list_attendance` already checked `start_date > end_date` and returned HTTP 422. This was examined and verified to work correctly.
